# スカウト送信の自動記録 — 現状まとめ

最終更新 2026-10-01 / 拡張バージョン v1.41.0

このファイルだけ読めば、別のチャットで続きの作業ができるようにまとめたもの。

---

## 1. 目的

**スプレッドシートへの手入力をやめること。**

いまはシートの手入力が正しい値で、自動記録はそれと突き合わせて検証している段階。
手入力をやめるには、手入力に依存しない検証手段を先に用意する必要がある（→ 6章）。

---

## 2. いまの仕組み

Chrome拡張（`taichi536/project1`、公開リポジトリ）。

### 送信の検知

以前は**押されたボタンの表示文字列の完全一致**で検知していた。媒体側が文言を変えると
その瞬間から記録が止まり、画面には何も出ないので誰も気づけない。実データで、ある担当者の
RDSだけ送信の36〜52%が記録されておらず、25分間に19件連続で消えた時間帯もあった。

いまは**送信の通信そのもの**を見ている。

| ファイル | 役割 |
|---|---|
| `net-hook.js` | `manifest` の `world: "MAIN"` でページ側の世界に読み込み、ページ自身の `fetch` / `XMLHttpRequest` を包む。POST かつ 2xx のとき `snowwe:request` イベントで content.js に渡す |
| `content.js` | `SEND_REQUESTS` / `BULK_SEND_REQUESTS` のURLに一致したら記録する |

`content.js` は拡張の隔離された世界で動くため、そこで `window.fetch` を包んでも
ページの通信は捕まえられない。だから別ファイルになっている。

登録済みの送信URL:

```
rds       /scouting/scoutroom/{id}/scout
bizreach  /v1/api/send-scout
dodax     /iapi/scout/bulkSendScout   ← 一括送信。本文から8桁の候補者IDを全部拾う
```

bizreach と doda X の一括送信は、**人が開発者ツールを開いて探したのではなく、
`scout_record_failures`（→ 下）の自己申告から分かった。**

### 候補者の識別と項目

**通信は「送信された」という合図としてだけ使う。** 候補者の識別子とプロフィール項目は
画面から取得した `pendingScout` から取る。

ここを間違えた事故がある。RDSの通信URLに含まれる `scoutroom/1678665` を候補者IDとして
使ったため、**別人が2人とも `rds_room_1678665` になった**。5分の重複排除が効いて、
同じ部屋で送った全員が1件に潰れるところだった。

### 記録先

| 先 | 状態 |
|---|---|
| Supabase `scouts` | 本番。RLSあり、公開鍵（anon）は**INSERT専用**。読むには `service_role` キーが必要 |
| Supabase `scout_record_failures` | 記録できなかったことの自己申告 |
| Supabase `extension_heartbeats` | 端末の生存報告（v1.38.0で追加。テーブル作成済 2026-10-01） |
| スプレッドシート | **自動書き込みは 2026-09-13（`40c6576`）で止まっている。** `queueGasScout` は呼ばれていない。いまシートにあるのは全部手入力 |

## 4. 原因の7分類

自動記録が合わない原因は、この7つに分けて考える。

| # | 分類 | 実例 | 検知手段 |
|---|---|---|---|
| A | **送信を感知できない**（漏れ） | ボタン文言一致でRDSが45%漏れ／一括送信は1通信で複数人／bizreachの送信APIが未登録だった | `scout_record_failures` ✅ |
| B | **同一人物と分からない**（識別子） | 部屋IDを候補者IDにして別人が同一IDに／dodaxで13/303がハッシュに落ちる／5分重複排除で再送が消える | **なし（盲点）** |
| C | **項目が取れない・誤る** | dodaxの会社名に氏名・会員番号が混入／全角の署名文が会社名に／`scout_message` がbizreach・dodaxで100%空 | 突き合わせの一致理由のみ |
| D | **誤って記録する**（過剰記録） | 日程調整の返信（`/iapi/message/saveByCorporate`）を送信と誤認／下書き・テンプレ保存・validate API／送信が失敗しても200なら記録 | 逆方向の突き合わせ ✅ |
| E | **記録したが届かない**（配送） | 失敗が8回続くと理由を問わず捨てていた（1分おきなので障害が8分続くと消える）／端末の時計ズレ | 生存報告の滞留件数（v1.38.0）／諦めた件の自己申告（v1.39.0）✅ |
| F | **突き合わせ側が誤っている**（検証） | RLSで0件→「100%漏れ」と**2回誤報告した**／`norm_univ` が接尾辞を1回しか削らず東工大大学院≠東工大／シート側の表記違い・媒体欄が空 | 一致理由を出すようにした ✅ |
| G | **運用・環境** | バージョンが1.27と1.36で混在／`content.js` はF5しないと反映されない／greenは未対応／担当者名が未設定 | 生存報告（v1.38.0）🔶 |

**「サイトの構造を捉えられていない」は分類ではなく、AとCの原因。** 媒体のUIは予告なく変わる
ので、変わったこと自体に気づける仕組み（A・Gの検知手段）がないと、静かに止まる。

**Fを先に疑うこと。** 自動記録は正しいのに「できていない」と判断したことが2回ある。

## 6. 手動記録をやめる条件

いま「正しいか」をシートの手入力で検証している。**手入力をやめた瞬間、この検証手段も消える。**
だから、やめる前に手入力に依存しない検証を1つ用意する必要がある。

現実的なのは **各媒体の送信履歴ページの件数と、自動記録の件数を日次で突き合わせる**こと。
RDS・doda X・bizreach いずれも送信履歴の画面があり、ポジション取得で既にページを読む
仕組み（`taichi536/scout` の `scripts/fetch_*.py`）がある。件数が合えば A（漏れ）と
D（過剰）が同時に潰れ、合わない日だけ調べればよくなる。

やめてよい条件:

1. 送信履歴件数との日次突き合わせが動いている
2. 確認済 ≈ 100%、未確認が低い、逆方向 ≈ 0
3. 生存報告で、全担当者の端末が最新版で生きている

## 8. 運用上の注意（何度も踏んだ罠）

- **`content.js` はページをF5しないと反映されない。** `chrome://extensions` の 🔄 は
  `popup.js` / `background.js` だけ。更新したのに直っていないと見えるのはこれが原因
- **Supabase の `scouts` を読むには `service_role` キーが必要**（公開鍵はINSERT専用）。
  キーはターミナルの環境変数にだけ置く。ファイルにもチャットにも貼らない
- 監査スクリプトは0件のときと401/403のときに**中断する**。そうしていなかったため
  「100%漏れ」と2回誤って報告した
- 大学名の正規化は接尾辞を**繰り返し**落とす（`東京工業大学大学院` → `東京工業大学`）
- 突き合わせは時刻ではなく**記録されている項目**（大学・会社）で行う。一致理由
  （`大学一致` / `会社一致` / `時刻のみ`）を必ず出す
- 媒体側の404は異常ではない場合がある（手動で作ったポジションなど）。それで
  アビームのポジションを全部閉じかけた

## 9. ファイル

### 拡張（`taichi536/project1`、ブランチ `claude/candidate-selection-system-em0otg`）

```
manifest.json                       バージョンと content script の登録
net-hook.js                         ページ側の通信を見る（world: "MAIN"）
content.js                          送信検知・プロフィール抽出・記録
  SEND_REQUESTS / BULK_SEND_REQUESTS  送信URL
  extractBasicInfo                    会社名・年齢・大学の抽出
  isMessageLine / isNotCompanyName     会社名として不適切な値を落とす
  recordScoutSent                      記録の入口（5分の重複排除あり）
  reportRecordFailure                  記録できなかったことの自己申告
  reportDodaxNameInCompany             会社名に氏名が連結されている報告
background.js
  flushSupabaseScoutQueue              記録の送信キュー（失敗時はバックオフ）
  moveToSupabaseDeadLetter             諦めた記録を端末に残し、自己申告する
  sendHeartbeat / getInstallId          生存報告（4時間おき＋起動時）
tools/audit_all_missing.py          シートとの突き合わせ監査
tools/sql/extension_heartbeats.sql  生存報告テーブルの定義と確認用クエリ
```
